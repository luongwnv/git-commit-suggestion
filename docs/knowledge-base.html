git-commit-suggestion — Knowledge Base

Non-obvious facts about providers, the pipeline, and VSCode integration. Append new gotchas here as you discover them; do not delete entries unless the underlying behavior changed.

Auto-fallback chain

The default provider: "auto" walks AUTO_CHAIN = ["pollinations", "duckduckgo", "huggingface", "mistral"] in orchestrator.ts, returning the first success. Ordering rationale:

  1. pollinations first — pure-OpenAI schema, no handshake, GPT-4o-class. Lowest friction.
  2. duckduckgo second — needs a vqd handshake (extra round-trip) but otherwise reliable; supports multiple frontier models.
  3. huggingface third — works without a key but per-IP rate-limited heavily; default model is a 7B which is sometimes worse at JSON.
  4. mistral last — consumes the bundled default key shared across all installs. If we burn it, everyone burns it.

When all four legs fail, the orchestrator throws a single error that lists every leg's failure reason. The webview surfaces this verbatim — useful for debugging because typically only one or two legs go down at a time.

Provider quirks

Pollinations.ai

  • POST to https://text.pollinations.ai/openai (NOT /v1/chat/completions). Schema is otherwise pure OpenAI.
  • No auth header. No API key concept.
  • Response Content-Type can be application/json (full OpenAI envelope) OR text/plain (just the model output). The provider handles both shapes.
  • Rate limit is ~1 request per 3-5 seconds per source IP; bursts get silently throttled (200 response with an empty/short body). If you get an empty response, wait a few seconds and retry.
  • Default model id is openai-large — Pollinations uses friendly names, not OpenAI's. Other useful values: openai (gpt-4o-mini), mistral, deepseek, qwen-coder.
  • Sponsored by the Pollinations community; service can vanish without notice. Treat success as a happy surprise, not a guarantee.

DuckDuckGo AI Chat

  • Two-step protocol:
    1. GET https://duckduckgo.com/duckchat/v1/status with header x-vqd-accept: 1; response header x-vqd-4 is the session token.
    2. POST https://duckduckgo.com/duckchat/v1/chat with x-vqd-4: <token>.
  • Response is SSE (data: {"message":"..."}\n lines); concat all message fields, ignore [DONE].
  • The vqd token rotates per session. If you get HTTP 418 ("I'm a teapot") it usually means the token expired or DDG bumped its handshake — refresh and retry.
  • DuckDuckGo does NOT support a separate system message; we concatenate system + user into a single user turn.
  • Models exposed: gpt-4o-mini, claude-3-haiku-20240307, meta-llama/Llama-3.3-70B-Instruct-Turbo, mistralai/Mistral-Small-24B-Instruct-2501, o3-mini. Map friendly names ↔ full names in duckduckgo.ts's MODELS dict.
  • User-Agent matters — endpoints reject empty or curl-default UAs. We send a Chrome-on-macOS UA.

HuggingFace router

  • OpenAI-compatible endpoint at https://router.huggingface.co/v1/chat/completions. The router fronts many backends (Inference Providers, Together, Fireworks, etc.) and picks one per model.
  • Free without a key but rate-limited per source IP — usually fine for occasional commit-message use, painful for batch.
  • Passing a HF token (from huggingface.co/settings/tokens) via Authorization: Bearer ... bumps quota and unlocks gated models.
  • Default model is Qwen/Qwen2.5-7B-Instruct — small, fast, good enough for short structured JSON. Override via gitCommitSuggestion.model: try meta-llama/Llama-3.3-70B-Instruct for higher quality.
  • Some models gated behind response_format: json_object compatibility; if you see "json_object not supported" in errors, switch model.

Bundled default Mistral key

Bundled in the .vsix. The repo ships a shared throwaway Mistral key in src/providers/default-keys.ts so first-time users can try the extension without signing up. This key is shared across all installs, rate-limited (~1 req/s on free tier), and will almost certainly be revoked or hit quota once the extension sees real usage. The webview shows a warning banner whenever this default is being used.
  • Key resolution order in orchestrator.ts: user-supplied key via SecretStorage → bundled default from default-keys.ts. User key always wins.
  • The banner ("⚠️ Using shared default key") is shown only when the active provider is mistral AND the user has no key set. Other providers have no bundled default; if they have no key they will fail with a clear ProviderError instead.
  • The two banner buttons map to webview → extension messages: { type: "open-mistral-console" } opens https://console.mistral.ai/api-keys in the OS browser; { type: "paste-key" } opens an InputBox and stores into SecretStorage.
  • If you fork this repo: replace the key in default-keys.ts with your own throwaway, or remove the file and return undefined from defaultKeyFor. Never ship a paid/production key here — anyone who downloads the .vsix can extract it in seconds.

Mistral free tier

  • Free tier rate limit is approximately 1 request/second per key. A second click within ~1s of the first will return HTTP 429.
  • Models on the free tier: mistral-small-latest (default), open-mistral-7b, open-mixtral-8x7b. Premier models (large-latest etc.) require a paid plan.
  • Use the OpenAI-compatible /v1/chat/completions schema with Authorization: Bearer <key>. response_format: { type: "json_object" } works.
  • Free tier opt-in checkbox at console.mistral.ai → Billing. Without it, the API returns 401 with a misleading message.

Anthropic — different schema

  • Endpoint is /v1/messages, not /chat/completions. The OpenAI-compatible class does not work here.
  • System prompt goes in a top-level system field, not in the messages array.
  • Auth header is x-api-key: <key> plus anthropic-version: 2023-06-01.
  • Response shape: { content: [{ type: "text", text: "..." }] }. Filter for type === "text" before reading text.
  • max_tokens is required. The extension uses 1500 — enough for 4-5 commit suggestions in JSON.

Ollama (local)

  • Endpoint is /api/chat. stream: false is required, otherwise the response is a sequence of NDJSON objects rather than one JSON body.
  • format: "json" nudges the local model into emitting valid JSON. Without it, small models (7B–8B) frequently fail JSON parsing.
  • Default base URL is http://localhost:11434. Override with gitCommitSuggestion.ollamaBaseUrl (e.g. remote box on LAN).
  • First call after Ollama startup can take 5–20 seconds while the model loads into RAM/VRAM. The progress notification stays open the whole time — this is expected.

Groq

  • OpenAI-compatible. Base URL is https://api.groq.com/openai/v1.
  • Free tier rate limits are much more generous than Mistral's (60 req/min on most models).
  • llama-3.1-8b-instant is fast and good enough for commit messages; llama-3.3-70b-versatile is better but slower.

g4f — unofficial reverse proxy

Risk acknowledged by the user. g4f-style endpoints scrape or proxy upstream provider sessions. Using them violates the upstream provider's Terms of Service, has no SLA, and historically some forks have shipped credential-stealing payloads. The extension gates this provider behind gitCommitSuggestion.enableUnofficialProviders and shows a modal warning before first use.
  • Endpoints rotate frequently. src/providers/g4f.ts ships a small list of community endpoints; if all fail, the orchestrator falls back to Mistral (so you still need a Mistral key configured for fallback to work).
  • Quality is typically GPT-3.5 level. For Conventional Commits this is usually fine; for longer body text it can hallucinate.
  • If you want to maintain your own endpoint list, fork FALLBACK_ENDPOINTS in src/providers/g4f.ts. Don't put endpoints in config/providers.yml if they require auth — that file is committed.

Pipeline quirks

Locating the git repo root

  • The workspace folder is NOT necessarily the git repo root — users routinely open a subfolder. Running git diff --cached from a non-repo cwd falls through to git diff --no-index mode, which then complains about unknown options (including --cached/--staged!) and prints a misleading "usage: git diff --no-index" block. This is the symptom users will report; the cause is "no repo at the cwd we passed", not a git-version issue.
  • We walk up from workspaceFolders[0] looking for a .git entry (directory or file — submodules and worktrees use a .git file). See findRepoRoot in src/utils/git.ts. We deliberately do NOT use git rev-parse --show-toplevel because it raises the same misleading no-index error when the cwd isn't a repo — we want a clean "not a git repo" message instead.
  • Use --cached not --staged in git diff. --staged was added in Git 2.18 (2018); --cached has worked since 1.6 (2008). The two are aliases. There's no upside to requiring the newer spelling.

Diff truncation

  • Token counting is a crude chars / 4 heuristic. The real tokenizer the provider uses will differ — pad your maxDiffTokens by 20% if you hit context-overflow errors.
  • Truncation order: sort files ascending by size, keep whole, until budget runs out. Then head-truncate the next file with a marker line. This biases toward "show many files at the cost of one large file" rather than "show one huge file at the cost of everything else".
  • Binary file diffs (Binary files differ) take negligible tokens and are always kept whole.

JSON parsing

  • LLMs ignore "no markdown fences" instructions ~10% of the time even with response_format: json_object. The parser strips ```json / ``` wrappers as the first step.
  • Some providers return { "suggestions": [...] } instead of a bare array. The parser handles both shapes.
  • If the LLM returns a non-Conventional-Commit type (e.g. "feature", "bugfix"), the parser falls back to chore rather than failing. This is intentional — partial output is better than nothing.
  • Scope is normalized: trimmed, lowercased, spaces → hyphens. Mirrors common Conventional Commits style.

SCM input box

  • The Git extension exposes repository.inputBox.value. Setting it triggers the SCM view to update — no manual refresh needed.
  • If multiple git repositories are open in the workspace, api.getRepository(uri) picks the one whose root contains the workspace folder. We fall back to repositories[0] if no match.
  • Embedded newlines in the input box render fine. No need to escape \n.

VSCode integration quirks

Secrets vs settings

  • API keys MUST go through context.secrets (encrypted, per-machine, never synced). Never via workspace.getConfiguration().update() — that writes to settings.json, which gets committed to dotfile repos.
  • The secret key format is gitCommitSuggestion.apiKey.<provider> (see SECRET_KEY in extension.ts). Don't change this without a migration step, or existing users will lose their keys silently.

Activation events

  • onStartupFinished is used so the status-bar lightbulb appears for every workspace. Activating on a command only would mean the button doesn't show until first invocation.
  • Cold activation is ~50ms; safe to do at startup.

Do NOT put `when` on a view contribution

The view in views.scm must NOT have a "when" clause. Context keys like scmProvider == git apply to menu contributions only (menus.scm/title, menus.view/title). On view contributions, an unmatched when silently hides the entire view — symptom: "Commit Suggestions doesn't appear in my SCM sidebar". Earlier in this project the view was hidden by exactly this mistake for several commits.
  • If you want the view conditional on something, control it from the extension side by calling vscode.commands.executeCommand("setContext", "myKey", value) from activate() and referencing "when": "myKey" — but that needs the custom key, not built-in SCM context keys.
  • The view always activates inside the SCM container. If the user's workspace isn't a git repo, the SCM container itself won't show anyway — no extra gating needed.

Webview view (sidebar GUI)

  • Registered as a WebviewView under the scm container (see "views.scm" in package.json). This puts it inside the existing Source Control sidebar — same view that already hosts the Changes list and the commit input box. No separate Activity Bar icon is added.
  • The HTML is rendered inline by CommitSuggestionViewProvider.renderHtml with a strict CSP: default-src 'none'; style-src ${webview.cspSource} 'unsafe-inline'; script-src 'nonce-...'. No external assets, no require/import inside the webview — VS Code's webview sandbox disallows both.
  • Communication is one-way per direction: extension → webview uses view.webview.postMessage({ type: "state", state }); webview → extension uses vscode.postMessage(...) via the acquireVsCodeApi() handle. There is no shared state and no synchronous bridge — every UI update is a full state replacement.
  • The webview holds NO suggestions of its own. The extension owns the canonical Suggestion[] in a suggestionsRef closure; on { type: "use", index } it looks up by index. This avoids round-tripping the diff/LLM-output back into the webview's JSON-serialized world.
  • Styling uses VS Code's theme CSS variables (--vscode-foreground, --vscode-button-background, etc.) so the view automatically matches Light/Dark/High-Contrast themes — never hard-code colours.
  • The view is initialized lazily: resolveWebviewView only fires when the user expands the view. The first { type: "ready" } message from the webview triggers an initial state post so the saved state (if any) is restored.

Repo layout principle

Layout mirrors index-crawl:

  • config/*.yml is the source of truth for anything declarative (endpoints, models, commit types, prompts). Code reads YAML at activation; do not hardcode.
  • src/models/ holds zod schemas; everything that crosses a boundary (LLM → us, settings → us, YAML → us) is validated.
  • src/providers/ is the "sources" layer (one class per backend). The orchestrator never sees provider-specific HTTP details.
  • src/pipeline/ is the orchestration layer — pure functions where possible.
  • docs/*.html instead of *.md on purpose: matches index-crawl's convention so AI agents reading both repos have the same expectation.
